[HIGH-1] MCPServerDiscovery: LiteLLM rejects server_name containing '.'
────────────────────────────────────────────────────────────────
STATUS: SHIPPED in v0.1.2 — helper + wire-boundary sanitization +
        Connection.spec.mcpToolPrefixSeparator field (commits
        20ade71, 44fb0cb, bfc0d8c). Residual bugs found in
        2026-05-22 prod smoke-test → FIX2.txt HIGH-1 (default
        direction wrong) and FIX2.txt HIGH-9 (manual MCPs regress
        on upgrade). Do NOT redo the helper work — extend it.

SYMPTOM
  All children spawned by a LiteLLMMCPServerDiscovery CR end up
  Ready=False, reason=LiteLLMRejected, message:
    "LiteLLM rejected POST /v1/mcp/server: litellm: 400 on POST
     /v1/mcp/server (code=400)"
  LiteLLM proxy returns:
    {"detail":{"error":"Server name cannot contain '.'.
     Use an alternative character instead Found: <name>"}}
  Reproduced on LiteLLM v1.85.1; 22/22 children of the toolhive
  discovery failed.

EVIDENCE
  - Discovery generates child metadata.name as
    "<discovery.spec.prefix>.<source-namespace>.<source-name>"
    (dotted DNS-1123 subdomain). Example child name:
        test-toolhive-discovery.mcp.context7
  - internal/controller/mcpserver_controller.go:360
        createReq := &litellm.MCPServerRequest{
            ServerName:    mcp.Name,
            Alias:         mcp.Name,  // D-7.1-10
            URL:           mcp.Spec.Endpoint,
            Transport:     mcp.Spec.Transport,
            ...
        }
    Both ServerName and Alias take mcp.Name verbatim — dots survive
    into the POST body.
  - Manual curl proves the constraint:
        POST /v1/mcp/server body={"server_name":"a.b","alias":"a.b",
                                   "url":"...","transport":"http"}
        → 400 {"detail":{"error":"Server name cannot contain '.'."}}
        POST same body with server_name="a-b","alias":"a-b"
        → 201 (server created)

ROOT CAUSE
  Mismatch between the operator's child-name generator (uses dotted
  DNS-1123 subdomain for K8s name uniqueness) and LiteLLM's
  server_name validator (forbids '.'). The dot is a valid K8s name
  character but not a valid LiteLLM server_name character.

FIX
  Sanitize ServerName + Alias at the moment of wire construction in
  internal/controller/mcpserver_controller.go (both CREATE and UPDATE
  arms — also lines ~388 for MCPServerUpdateRequest). Pure-data
  transform; do NOT change mcp.Name on the K8s side.
  Concretely:
        sanitizedName := strings.ReplaceAll(mcp.Name, ".", "-")
        createReq := &litellm.MCPServerRequest{
            ServerName: sanitizedName,
            Alias:      sanitizedName,
            ...
        }
  Apply the same sanitize to the UPDATE arm (~line 388) and to any
  delete-by-name path that calls LiteLLM. Make the sanitize a helper
  in internal/litellm/ so future call sites pick it up:
        // sanitizeMCPServerName replaces every '.' with '-'.
        // LiteLLM v1.83.10+ rejects '.' in server_name.
  Leave the K8s metadata.name alone — the dotted form is the
  documented Discovery name template (CONTEXT.md / spec §6.5).
  Record the divergence between the K8s-side name and the LiteLLM-side
  server_name in status.lastRendered if not already there, so users
  can debug.

TEST PLAN
  1. Unit test in internal/controller/mcpserver_controller_test.go
     that constructs an MCPServer with Name="a.b.c" and asserts the
     captured fake-LiteLLM-client request has ServerName=Alias="a-b-c".
  2. envtest that POSTs a Discovery-generated MCPServer with a dotted
     name to a mock LiteLLM and asserts Ready=True (no 400 propagation).
  3. E2E (kind + mock LiteLLM): create LiteLLMMCPServerDiscovery
     against a fake toolhive index returning 3 servers in 2
     namespaces; assert all 3*2=6 dotted children reach Ready=True
     within 60s.

[HIGH-2] KubeAI discovery: children miss api_base
────────────────────────────────────────────────────────────────
STATUS: SHIPPED in v0.1.2 (commits eafe468, cbe44ff). Verified
        2026-05-22 prod smoke-test — kubeai children now carry
        spec.params.api_base. Children still hit LiteLLMRejected at
        registration, but the cause is upstream LiteLLM /
        hosted_vllm config, not the missing api_base — tracked
        separately as FIX2.txt LOW-6 (observability).

SYMPTOM
  Children of a kubeai LiteLLMModelDiscovery register at LiteLLM
  successfully (Ready=True) but contain no api_base in spec.params.
  Inference-time requests fail because LiteLLM has no route for
  hosted_vllm/<id>. Test repro:
    Discovery spec.baseUrl: http://kubeai.kubeai.svc/openai/v1
    Child spec.params: {model: hosted_vllm/qwen3-4b}   ← no api_base
    Autoconfig parity:
    {model: hosted_vllm/qwen3-4b,
     api_base: http://kubeai.kubeai.svc/openai/v1,
     rpm: 25, timeout: 300, stream_timeout: 60}

EVIDENCE
  - Operator's kubeai provider (internal/providers/kubeai.go) only
    uses cfg.BaseURL to drive the discovery's own GET /v1/models call;
    it never propagates the value into the generated child Model spec.
  - For bedrock, the operator DOES auto-overlay spec.region into each
    child's spec.params.aws_region_name (see CONTEXT.md D-07; the
    "operator's only typed-field overlay"). KubeAI got no equivalent
    overlay despite needing one for runtime routing.
  - Workaround that works today: user manually replicates baseUrl into
    discovery.spec.params.api_base — verified to propagate. Confirms
    the propagation bag is fine; the gap is just "no automatic
    overlay".

ROOT CAUSE
  Operator design currently overlays only aws_region_name for bedrock.
  KubeAI's api_base is functionally the same role (routing target the
  child needs at inference time) but no overlay rule was added.

FIX
  Add a second typed-field overlay rule, parallel to the bedrock one,
  for type=kubeai:
    - When LiteLLMModelDiscovery.spec.type == "kubeai", the reconciler
      writes spec.params.api_base = LiteLLMModelDiscovery.spec.baseUrl
      into every generated child Model BEFORE the propagation bag
      merge (so the user CAN still override via discovery.spec.params
      if they really want a different api_base).
  Update CONTEXT.md D-07 to list both overlays (bedrock region +
  kubeai api_base). Add a CR-level CEL validator: when type=kubeai,
  spec.baseUrl is REQUIRED (currently already enforced — confirm in
  api/litellm/v1alpha1/modeldiscovery_types.go).

TEST PLAN
  1. Unit test: kubeai Discovery with baseUrl="http://x/openai/v1"
     and one upstream model "foo" produces a child Model with
     spec.params == {"model": "hosted_vllm/foo", "api_base":
     "http://x/openai/v1"} (plus any user-supplied params merged on
     top).
  2. Unit test: user-supplied discovery.spec.params.api_base="http://y"
     wins over the auto-overlay (no double-write, no overlay error;
     the spec value takes precedence — match bedrock region behavior).
  3. E2E: deploy a kubeai mock + a real LiteLLM in kind; create the
     Discovery; issue a chat completion against the child's model_name
     and assert 200 OK with the mock as upstream.

[MEDIUM-3] MCPServer/Connection: no auto-recovery after upstream
            restart or upgrade
────────────────────────────────────────────────────────────────
STATUS: PARTIAL — backoff cap (432f680) + Connection-Ready watch
        (b1dc4a9) shipped in v0.1.2. Verified in prod 2026-05-22:
        watch fires on TRANSITION, not on cold-cache hydration, so
        Team/A2AAgent stuck "Connecting" after operator restart →
        FIX2.txt MEDIUM-3 (cold-start race). Also no retry on
        deterministic 4xx → FIX2.txt HIGH-2 (sticky status).

SYMPTOM
  After redeploying LiteLLM (image bump from main-latest to v1.85.1),
  an existing LiteLLMMCPServer that had been failing with a transient
  500 stayed in the backoff queue and did not retry inside the
  observation window (~minutes). Manual delete + reapply was needed
  to nudge a fresh reconcile.

EVIDENCE
  - Reconciler error path in mcpserver_controller logs:
      "transient error from LiteLLM; returning for backoff"
    with controller-runtime's default exponential backoff (no cap).
  - LiteLLMConnection probe at the same time succeeded, but the MCP
    controller never observed that the upstream became healthy — it
    is driven by its own queue with no fan-in from the Connection's
    Ready-flip event.

ROOT CAUSE
  Two coupled issues:
  (a) controller-runtime default backoff is unbounded — after a few
      transient errors the next retry can be 5-10 min out.
  (b) MCPServer (and likely Model, A2AAgent) controllers do not watch
      for LiteLLMConnection.status.conditions[Ready].lastTransitionTime
      to flip True; they only react to their own CR mutations.

FIX
  Two surgical changes:
  (a) Cap exponential backoff at ~30s in the rate-limiter for transient
      errors. Use workqueue.NewItemExponentialFailureRateLimiter(
        baseDelay=200ms, maxDelay=30s)
      explicitly when registering the reconciler. Keep the unbounded
      backoff for non-transient errors (LiteLLMRejected, SecretNotFound)
      so those don't hot-loop.
  (b) Add a Watches() on LiteLLMConnection in mcpserver_controller,
      model_controller, a2aagent_controller, team_controller setups —
      map a Connection's Ready=True transition to enqueue all child
      CRs in the same namespace. The connection.Cache already broadcasts
      a snapshot signal; reuse that channel.

TEST PLAN
  1. envtest: introduce a deterministic transient error from the fake
     LiteLLM (500 for first N requests, 201 thereafter). Assert that
     the controller recovers within <=60s wall-clock without external
     mutation.
  2. envtest: with a failing LiteLLMConnection, create an MCPServer.
     Flip the Connection Ready=True. Assert MCPServer reconciles and
     reaches Ready=True within <=10s.

[MEDIUM-4] Ready=True does not validate reachability
────────────────────────────────────────────────────────────────
STATUS: DEFERRED to roadmap (commit 033a0f9 records reachability
        probe as a deferred SPEC phase). Not blocking — Ready=True
        false positives remain the trade-off in v1alpha1. No
        FIX2.txt successor entry.

SYMPTOM
  False positives on three kinds:
  (a) LiteLLMA2AAgent with endpoint pointing at a Service that does
      not exist (e.g. http://noop-agent.ackstorm.svc:9001) → Ready=True
      because LiteLLM POST /v1/agents returned 201 — but the actual
      A2A endpoint is unreachable from the LiteLLM pod, so any agent
      invocation fails at runtime.
  (b) LiteLLMModel with provider creds that allow registration but
      block inference (Bedrock IAM that can List but not Invoke; an
      OpenAI key with the wrong project; a Gemini key without the
      requested model in its allowlist).
  (c) LiteLLMMCPServer with a transport+url combination LiteLLM
      accepted at registration but cannot actually open a session to
      (Exa, internal MCP gateways behind auth, etc.).

EVIDENCE
  - Reconcilers gate Ready=True purely on the POST /<endpoint> 2xx
    response from LiteLLM. There is no follow-up probe.
  - Operator already does a control-plane probe at the Connection
    layer (CONN-03's "GET /models" call) — this MEDIUM is about
    extending the same idea to per-CR validation.

ROOT CAUSE
  By design v1alpha1 — the operator owns LiteLLM-side registration
  and trusts LiteLLM as the source of truth. The inference-time
  failure mode is invisible to the operator's reconcile loop.

FIX
  Phase 4-5 candidate, NOT a fast fix. Two paths:
  (a) Per-kind optional `spec.probe: {enabled: true}` flag that
      triggers a synthetic inference call after registration succeeds.
      Add a new status condition `type=Probed, status=True/False,
      reason=ProbeOK|ProbeFailed|ProbeSkipped` separate from Ready
      so existing semantics don't shift. Cost: real upstream API
      calls on every reconcile that flips probe.enabled on.
  (b) Surface LiteLLM's own per-server health endpoint when it exists
      (LiteLLM v1.85.1 has /v1/mcp/server/health which the proxy
      already polls — same data could feed status.healthCheck).

TEST PLAN
  1. Unit/envtest matrix per kind: create CR with dummy endpoint,
     enable probe=true, assert Ready=True + Probed=False with reason
     ProbeFailed.
  2. Same matrix with reachable endpoint → Probed=True.

[LOW-5] Discovery orphan GC is slow relative to filter mutation
────────────────────────────────────────────────────────────────
STATUS: SHIPPED in v0.1.2 (commit 4c33474 — prune-on-filter-mutation
        regression test + reconciler change). Verified 2026-05-22:
        patching test-anthropic-discovery with exclude pattern
        dropped 9 → 3 children within seconds, no 6-min wait.

SYMPTOM
  After narrowing spec.filters.exclude on a LiteLLMModelDiscovery,
  stale children (those that no longer match) take minutes to be
  deleted. Live evidence: openai discovery patched at 08:34Z went
  117 → 49 children only after ~6 min wall-clock; the discovery's
  status.generatedCount flipped to 49 immediately but the K8s child
  set caught up much later.

EVIDENCE
  - Prune appears to be triggered by the refresh.interval tick
    (defaulted to 10m, MDISC-05 floor 1m), not by the CR's own
    generation change.
  - Children remained Ready=True but were no longer "owned" by the
    discovery's current rendered set — they hung around until refresh.

ROOT CAUSE
  Refresh-driven prune loop in modeldiscovery_controller; spec.filters
  mutation does not directly drive a prune pass.

FIX
  In modeldiscovery_controller.Reconcile, after re-rendering the
  expected child set, ALWAYS run the prune pass — not only on the
  refresh-interval branch. Idempotent: if expected == actual the
  prune pass is a no-op.
  Same applies to MCPServerDiscovery if it shares the pattern.

TEST PLAN
  1. envtest: create a discovery yielding 5 children. Mutate
     spec.filters.exclude to drop 3. Assert ChildList → 2 within <=
     reconcile latency (sub-second), without waiting for refresh.

[LOW-6] OpenAI discovery: "canonical only" pattern undocumented
────────────────────────────────────────────────────────────────
STATUS: SHIPPED in v0.1.2 (commit 6c372e7 — commented exclude
        pattern in examples/example-deploy/03-modeldiscovery.yaml).
        Extended 2026-05-22 with anthropic / bedrock / gemini /
        kubeai blocks. Anthropic uses provider-specific regex
        ".*-[0-9]{8}$" not the OpenAI ".*[0-9]$" — documented in
        the file.

SYMPTOM
  ackstorm-litellm-autoconfig hard-codes a pre-filter that drops every
  OpenAI model whose id ends in a digit:
      pre_filtered = [m for m in models if not m.id[-1].isdigit()]
  This removes the dated variants (gpt-4o-mini-2024-07-18,
  gpt-4.1-mini-2025-04-14, ...) and leaves only the rolling aliases.
  Our operator does NOT do this; the user has to discover it. The
  equivalent in our CR is:
      filters:
        exclude: [".*[0-9]$"]
  Works (drops from 117 to 49) but is not documented anywhere.

EVIDENCE
  Manual experiment with the four discoveries on EKS, 2026-05-22.
  Counts before/after the regex exclude match autoconfig parity 1:1.

ROOT CAUSE
  No documented pattern in the example manifests
  (examples/example-deploy/03-modeldiscovery.yaml) for the
  "canonical OpenAI variant only" use case.

FIX
  Cheapest: add a comment block + commented-out exclude line in the
  example openai discovery showing the canonical-only pattern.
  Medium: introduce a typed flag spec.openai.canonicalOnly (or a
  generic spec.canonicalOnly that means "id last char is not a
  digit") and let the reconciler add the pattern itself.

TEST PLAN
  1. Doc-only PR: add the comment + example. No code test needed.
  2. If typed flag path: unit test asserts canonicalOnly=true plus
     no explicit exclude == produces the same child set as explicit
     exclude=["[0-9]$"].

[LOW-7] ToolHive informer: noisy "v1alpha1 wins" dedup log
────────────────────────────────────────────────────────────────
STATUS: SHIPPED in v0.1.2 (commit 49134c7 — throttle to
        once-per-60s/tuple). VERIFICATION FAILED 2026-05-22:
        operator still logs 22 lines per reconcile in prod. The
        throttle key or window is broken → FIX2.txt MEDIUM-4.
        Also FIX2.txt LOW-11: informer registers v1alpha1 only,
        never v1beta1.

SYMPTOM
  Operator log spam on every reconcile when watching a namespace with
  toolhive MCPServers:
    INFO toolhive-informer toolhive dedup: v1alpha1 wins
      {kind: MCPServer, namespace: mcp, name: <each-server>,
       dedup_reason: alpha_wins}
  One line per MCPServer per reconcile loop. 22 servers × poll
  interval = a lot of log churn.

EVIDENCE
  Repeated across many distinct reconcile IDs in the prod operator
  log (07:40Z startup logged the deprecation warning
    "toolhive.stacklok.dev/v1alpha1 is deprecated; use v1beta1"
  immediately, then the dedup line spam started).

ROOT CAUSE
  The operator subscribes to both v1alpha1 and v1beta1 of toolhive
  MCPServer (per startup log "toolhive informer registered" for both
  GVKs). The dedup step picks v1alpha1 every time even though v1beta1
  is the cluster's storage version, and logs at INFO every pick.

FIX
  Two surgical options:
  (a) Drop the v1alpha1 informer entirely if v1beta1 is available at
      startup. Detect via the apiserver's resource discovery (a
      RESTMapper hit). Falls back to v1alpha1 only when v1beta1 is
      not served. Wire the choice once at startup, not per reconcile.
  (b) If keeping the dedup, demote the log to V(2) or move it behind
      a flag so production runs are quiet. The dedup itself should
      log once-per-unique-name in a 60s window, not every reconcile.

TEST PLAN
  1. Unit test: with both v1alpha1 and v1beta1 served by the fake
     apiserver, only one informer is registered (whichever option
     above is chosen).
  2. Log sampling: ten reconcile cycles produce ≤1 dedup log line
     per unique (kind, namespace, name) tuple per minute, not 10×N.

[STATUS] FIX.txt remediation post-mortem (2026-05-22)
────────────────────────────────────────────────────────────────

The FIX.txt findings shipped in v0.1.2 via the prior plan
(docs/plans/2026-05-22-fix-txt-remediation.md). Post-deploy smoke
test against EKS revealed regressions and residual gaps documented
in FIX2.txt; the v0.1.3 branch fix/fix2-txt-remediation lands the
real fixes. STATUS per FIX.txt entry:

  HIGH-1   SHIPPED v0.1.2 (sanitizer + Connection.spec field added).
           SUPERSEDED by FIX2 HIGH-1 (default-direction was wrong;
           "-" forbade hyphens, but LiteLLM v1.85.1 rejects ".") and
           FIX2 HIGH-9 (sanitizer mangled already-safe inputs). Final
           fix in v0.1.3 (commit 8482eac on fix/fix2-txt-remediation).

  HIGH-2   SHIPPED v0.1.2 (KubeAI discovery now seeds api_base).
           No FIX2 follow-up.

  MEDIUM-3 SHIPPED v0.1.2 (connectionReadyTransition predicate +
           connectionTo<Kind> mapping). SUPPLEMENTED by FIX2 MEDIUM-3
           (predicate extended to fire on GenericEvent) and FIX2
           HIGH-2 (BootSweeper covers cold-start re-reconcile for
           CRs whose connection is already Ready at boot).

  MEDIUM-4 SHIPPED v0.1.2 (active probe added). No FIX2 follow-up.

  LOW-5    SHIPPED v0.1.2 (discovery vanish-detection tightened).
           No FIX2 follow-up.

  LOW-6    SHIPPED v0.1.2 (OpenAI canonical-only filter pattern
           documented). UNRELATED to FIX2 LOW-6 (new Prometheus
           counter); the slot reuse is incidental.

  LOW-7    SHIPPED v0.1.2 (per-tuple dedup throttle implemented).
           SUPPLEMENTED by FIX2 MEDIUM-4 (throttle math was correct
           but operationally noisy at V(0); FIX2 demotes to V(2)
           and adds a coalesced V(0) summary at most once per 5m).
