    v0.3.0 migration — MCPServerDiscovery naming¶

    This release renames the children produced by LiteLLMMCPServerDiscovery from <discovery>.<source-namespace>.<source-name> (three dotted components) to <spec.prefix>-<source-name> (two hyphen-separated components). The change mirrors LiteLLMModelDiscovery's naming convention exactly — pre-v0.3.0 LiteLLMMCPServerDiscovery was the only discovery kind with an asymmetric three-part name.

    Breaking changes¶

    1. spec.prefix is now a required field on LiteLLMMCPServerDiscovery. Existing CRs without spec.prefix will fail validation on kubectl apply after upgrade.
    2. All currently-managed K8s MCPServer child CRs will be deleted on upgrade (their finalizer fires → DELETE /v1/mcp/server/<id> on the LiteLLM side → fine) and recreated under the new name → POST /v1/mcp/server registers fresh records on the LiteLLM side.
    3. The LiteLLM-side records under the OLD names become orphans. The operator does NOT auto-clean these (LiteLLMMCPServerDiscovery never calls LiteLLM per MSDISC-16; the child controller's adoption logic resolves by URL+transport only on its own reconcile path). Manual cleanup is required — see below.
    4. Cross-discovery collisions are now the user's responsibility via spec.prefix. The pre-v0.3.0 auto-disambiguation logic relied on the source-namespace component to keep names unique across discoveries; that crutch is gone. Pick distinct prefixes per discovery (e.g. mcp, toolhive, team-alpha).

    Pre-upgrade checklist¶

    1. Add spec.prefix to every LiteLLMMCPServerDiscovery CR in your gitops tree:
    apiVersion: litellm.ackstorm.ai/v1alpha1
kind: LiteLLMMCPServerDiscovery
metadata:
  name: mcp
spec:
  prefix: mcp   # <-- add this line
  type: toolhive
  toolhive:
    namespaces: [mcp]
  refresh:
    interval: 1m

    1. Pick non-colliding prefixes across all your LiteLLMMCPServerDiscovery CRs. The operator no longer disambiguates via source-namespace — if two discoveries with the same prefix target the same upstream name, the K8s-native DuplicateDiscovery skip will fire and the second occurrence will be dropped.

    2. Plan for orphan cleanup on the LiteLLM side (see "Orphan cleanup" below).

    Intra-discovery NameCollision¶

    If two upstream ToolHive objects from different namespaces produce the same <spec.prefix>-<source-name> child name within a SINGLE discovery (e.g. mcp/foo and tools/foo both rendered as mcp-foo under a discovery with prefix: mcp and namespaces: [mcp, tools]), the operator will:

    • Skip the second occurrence (the first wins, deterministic by ToolHive list iteration order).
    • Surface a parent-level status condition: 
      status:
  conditions:
    - type: NameCollision
      status: "True"
      reason: NameCollision
      message: 'intra-discovery source-name collision(s) detected: "foo" (ns "tools" vs first-seen ns "mcp") — rename one upstream or split the discovery (FIX4 H-2)'
    • Record the offending candidate in status.skippedCandidates[Reason=NameCollision].

    Resolve by either: - Renaming one of the upstream ToolHive objects so the source names are unique within the discovery, OR - Splitting the discovery into two LiteLLMMCPServerDiscovery CRs with distinct spec.prefix values (one per source namespace).

    Orphan cleanup (LiteLLM side)¶

    After the upgrade reconciles, the LiteLLM admin UI's MCP Servers table will show TWO entries per upstream: the old one under the dotted name (e.g. mcp.mcp.aws-knowledge) AND the new one under the hyphenated name (e.g. mcp-aws-knowledge). Only the new entry is reconciled by the operator going forward — the old one is an orphan.

    Manual cleanup options:

    Option A — LiteLLM admin UI. Open the MCP Servers table, filter or sort by created_at, and delete the older entries by hand.

    Option B — HTTP API. Loop through the server list and delete the dotted ones:

    LITELLM_URL=https://your-litellm.example.com
LITELLM_MASTER_KEY=sk-...

curl -sS -H "x-litellm-api-key: $LITELLM_MASTER_KEY" \
  "$LITELLM_URL/v1/mcp/server" \
| jq -r '.[] | select(.server_name | test("\\.")) | .server_id' \
| while read -r id; do
    echo "deleting orphan $id"
    curl -sS -X DELETE \
      -H "x-litellm-api-key: $LITELLM_MASTER_KEY" \
      "$LITELLM_URL/v1/mcp/server/$id"
  done

    The test("\\.") jq filter matches server_name values containing a literal dot — the pre-v0.3.0 dotted scheme used dots; the new scheme uses hyphens only.

    Option C — Wait. LiteLLM does not auto-expire stored MCP server records; orphans persist indefinitely. They cost nothing beyond visual clutter in the admin UI.

    Verification post-upgrade¶

    # All child MCPServer CRs use the new naming.
kubectl get litellmmcpserver -A -o jsonpath='{.items[*].metadata.name}' | tr ' ' '\n'
# Expect names like "mcp-aws-knowledge", NOT "mcp.mcp.aws-knowledge".

# No NameCollision condition fired.
kubectl get litellmmcpserverdiscovery -A -o jsonpath='{.items[*].status.conditions[?(@.type=="NameCollision")]}'
# Expect every condition to show status=False reason=NoCollisions.

# LiteLLM UI: "Created By" column shows "alitellm-operator/0.3.0"
# on every operator-managed Model row (FIX4 H-1 separate fix that
# also ships in v0.3.0).
