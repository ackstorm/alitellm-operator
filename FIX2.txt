[HIGH-1] mcpToolPrefixSeparator default `-` produces WRONG-direction
         sanitization against LiteLLM v1.85.1
────────────────────────────────────────────────────────────────
SYMPTOM
  After v0.1.2 (which ships SanitizeMCPServerName + the new Connection
  field spec.mcpToolPrefixSeparator), all 22 MCPServerDiscovery children
  still fail with the EXACT same 400 as FIX.txt HIGH-1:
    POST /v1/mcp/server → 400 "Server name cannot contain '.'."
  Repro:
    kubectl annotate litellmmcpserver test-toolhive-discovery.mcp.context7 \
      -n ackstorm test/force-reconcile=$(date -Is) --overwrite
    # operator log: 13:35:41Z "LiteLLM rejected request" op="POST /v1/mcp/server"
    # status: lastTransitionTime unchanged (same condition content)

EVIDENCE
  - LiteLLM v1.85.1 deployed in cluster, MCP_TOOL_PREFIX_SEPARATOR
    visibly NOT overridden — confirmed by FIX.txt evidence
    "Server name cannot contain '.'.".
  - api/litellm/v1alpha1/litellmconnection_types.go:69
        // +kubebuilder:default:="-"
    Default value is "-".
  - internal/litellm/sanitize.go:34
        case "", MCPToolPrefixSeparatorDefault:  // ""→"-"
            return strings.ReplaceAll(name, "-", ".")  // wrong direction
  - The cluster's LiteLLMConnection/default has no explicit value:
        spec:
          endpoint: http://litellm.litellm.svc:4000
          masterKeySecretRef: { ... }
        # mcpToolPrefixSeparator: <unset → default "-">
  - With separator="-", sanitizer replaces "-" with "." in
        test-toolhive-discovery.mcp.context7
    yielding
        test.toolhive.discovery.mcp.context7
    which is exactly the kind of name LiteLLM rejects.

ROOT CAUSE
  The default ("-") encodes the assumption that LiteLLM also defaults
  MCP_TOOL_PREFIX_SEPARATOR to "-" AND therefore forbids "-" in
  server_name. Empirically on this cluster's LiteLLM v1.85.1, the
  validator forbids "." regardless of env-var configuration — so the
  default direction is wrong for the most common deploy.
  Code comment in sanitize.go:38 reads "matches LiteLLM's own default"
  but the upstream behavior observed is the opposite.

FIX
  Two options — pick one explicitly:
  (a) Flip the default from "-" to "." in
      api/litellm/v1alpha1/litellmconnection_types.go:69 so OOTB
      deploys against an unmodified LiteLLM v1.85.1 work without the
      user knowing about the field. Update CRD + Helm rendered CRD,
      add release note flagging the behavior change for users who
      relied on the old default.
  (b) Detect the LiteLLM-side separator at probe time
      (LiteLLM exposes `MCP_TOOL_PREFIX_SEPARATOR` via /health/config
      or the server response includes it in the rejection message).
      Surface it into Connection.status.mcpToolPrefixSeparator and
      use that, treating spec.mcpToolPrefixSeparator only as override.
      Removes the foot-gun entirely.
  Either way: error message from LiteLLM ("Server name cannot
  contain '<X>'.") should be parsed and echoed into status.message
  to make the misconfig diagnosable from `kubectl describe` alone.

TEST PLAN
  1. Unit test: a LiteLLMConnection with no explicit
     spec.mcpToolPrefixSeparator and the operator running against a
     LiteLLM that forbids "." produces sanitized names with no "."
     characters. (Drives the default-flip in option (a).)
  2. E2E: same setup as FIX.txt HIGH-1 test plan, but using a real
     LiteLLM v1.85.1 image with default MCP_TOOL_PREFIX_SEPARATOR.
     Currently 0/22 children Ready; target is 22/22.
  3. Regression test: a Connection with explicit
     spec.mcpToolPrefixSeparator="-" against a LiteLLM that forbids "-"
     still produces dotted names (i.e. the override knob still works).

WORKAROUND (operator-side, until fix)
  kubectl patch litellmconnection default -n ackstorm --type=merge \
    -p '{"spec":{"mcpToolPrefixSeparator":"."}}'

[HIGH-2] Stale-status sticky after upstream-rejection: no auto-retry
         on operator restart
────────────────────────────────────────────────────────────────
SYMPTOM
  Every CR that hit a 4xx from LiteLLM (LiteLLMRejected) BEFORE the
  v0.1.2 upgrade stays at status.conditions[Ready]=False with the
  ORIGINAL lastTransitionTime, even after the operator pod restarts
  on the new version that contains the fix. The reconciler must be
  poked (annotation bump, spec edit) to retry.
  Concrete prod evidence (after 2026-05-22T13:31Z restart on v0.1.2):
    - 22/22 MCPServerDiscovery children:    lastTransitionTime 08:19:07Z
    - 6/18  Bedrock models (e.g. nova-lite): 09:53:34Z
    - 38/56 OpenAI models:                   ~08:30Z
    - 12/27 Gemini models:                   ~08:30Z
    - 4/4   KubeAI models:                   ~08:30Z

EVIDENCE
  - kubectl get on all CRs shows AGE > 4h yet conditions stamps from
    that initial creation, despite Operator pod AGE = 3m29s.
  - controller-runtime resync DOES enqueue these objects on operator
    boot (informer cache rehydration). The reconciler runs but writes
    back the SAME condition (Ready=False, reason=LiteLLMRejected)
    → k8s deduplicates: lastTransitionTime unchanged → looks "stale".
  - Commit b1dc4a9 (Watches() on Connection Ready transition) only
    fires on actual transition; Connection has been Ready=True
    continuously, so no event ⇒ no enqueue.
  - Commit 432f680 (backoff cap 30s) prevents hot-loops but doesn't
    drive periodic re-attempts on errors after the controller has
    stopped re-queuing.

ROOT CAUSE
  Two coupled effects:
  (a) controller-runtime's exponential rate-limiter eventually stops
      re-enqueuing items whose result has not changed. Capping at 30s
      means "retry no slower than every 30s WHILE in the queue", not
      "always retry every 30s forever".
  (b) The reconciler returns ctrl.Result{} (no RequeueAfter) for
      LiteLLMRejected errors — they are treated as "deterministic"
      and never retried until something else (CR mutation, owner
      reconcile, Connection Ready flip) triggers an enqueue.

FIX
  Recommended:
  - For non-deterministic upstream errors (5xx, network) → keep
    capped-backoff requeue (already done).
  - For deterministic upstream errors (4xx, LiteLLMRejected,
    SecretNotFound) → return ctrl.Result{RequeueAfter: 5*time.Minute}
    so a slow background poll still catches "the upstream changed
    its mind" (model added to allowlist, IAM grant added, config
    reloaded). 5 min is a sane default — make it configurable via
    Connection.spec.requeueOnRejectedAfter (default 5m, min 1m).
  - On operator boot, force one extra reconcile pass on every CR
    whose status.observedGeneration matches but Ready=False. This is
    cheap (the reconciler is idempotent) and recovers the
    upgrade-fixes-things-but-status-sticky scenario observed here.

TEST PLAN
  1. envtest: create a CR that hits 400 once, fix the fake LiteLLM
     to accept, wait the configured requeueOnRejectedAfter, assert
     Ready=True without external mutation.
  2. envtest: operator restart with rejected CRs in cluster — assert
     each CR reconciles within 30s of pod Ready, and that successful
     CRs flip Ready=True without intervention.

[MEDIUM-3] Cold-start race: Connection-watch fires "Connecting"
           state to Team/A2AAgent reconcilers; never recovers
────────────────────────────────────────────────────────────────
SYMPTOM
  After operator pod restart on v0.1.2:
    test-team             False  LiteLLMUnavailable  "LiteLLMConnection/default not Ready (reason: Connecting)"
    test-noop-agent       False  LiteLLMUnavailable  "LiteLLMConnection/default not Ready (reason: Connecting)"
  Both transitioned at 13:31:59Z (operator startup + ~30s) and stay
  stuck even though LiteLLMConnection/default went Ready=True at
  13:31:32Z and has been Ready ever since.

EVIDENCE
  - Connection status:
        type: Ready, status: True, reason: Synced,
        lastTransitionTime: 07:57:31Z  (NOT the 13:31 restart time)
    So from the apiserver's POV, the Connection has been Ready since
    08:00. The "Connecting" message came from the Connection cache's
    INITIAL state during operator boot before the probe succeeded.
  - Team + Agent reconcilers ran during that boot window, saw
    "Connecting" via the cache, wrote LiteLLMUnavailable + Connecting.
  - The connection-Ready watch (commit b1dc4a9) fires on STATE
    TRANSITION (False→True). The transition from "no entry" to True
    on cold-start may not produce a watch event for child reconcilers
    because the cache snapshot lands without firing the event channel
    or because the child reconciler races the cache write.

ROOT CAUSE
  Connection cache snapshot initialization is not atomic with the
  child reconciler dependency on it. There's a window where the
  child sees "Connecting" and writes a False status, then never
  re-reconciles because:
    (a) the Connection's Ready=True transition fired its event
        BEFORE the child reconciler subscribed to that channel, OR
    (b) the child reconciler subscribed but the event was a single
        edge that landed in the void.
  The watch in mcpserver_controller / model_controller /
  team_controller / a2aagent_controller SetupWithManager needs to
  enqueue ALL children when the Connection's Ready edge is seen
  AND on the FIRST cache-snapshot publish, not only on
  False→True transitions.

FIX
  In each controller's SetupWithManager, register Watches() on
  LiteLLMConnection with a predicate that fires on:
    - CreateEvent (cold cache hydration)
    - UpdateEvent where oldReady != newReady
    - GenericEvent from the connection cache's snapshot channel
  Map each fired event to an EnqueueRequestsFromMapFunc that lists
  all matching child CRs in the same namespace.
  Also: when the reconciler observes the Connection's cached
  Ready=true after a previous Ready=false snapshot from the same
  pod lifetime, force one Re-reconcile regardless of CR generation.

TEST PLAN
  1. envtest with controlled timing: bring up Connection in
     Connecting state, create Team. Wait. Flip Connection to Ready.
     Assert Team reaches Ready=True without restarting the operator.
  2. envtest cold-start: pre-seed apiserver with a Ready Connection
     and a non-reconciled Team. Start operator. Assert Team reaches
     Ready=True without intervention within 60s.

WORKAROUND
  kubectl annotate litellmteam test-team -n ackstorm \
    test/force-reconcile=$(date -Is) --overwrite
  kubectl annotate litellma2aagent test-noop-agent -n ackstorm \
    test/force-reconcile=$(date -Is) --overwrite

────────────────────────────────────────────────────────────────

    "LiteLLM rejected POST /<endpoint>: litellm: 400 on POST
     /<endpoint> (code=400)"
  for every 4xx — model rejection, MCP server_name validation,

        Message: LiteLLM rejected POST /model/update: litellm: 400 on POST /model/update (code=400)

    the operator log at the moment of the call but is not threaded
    into the condition message.

ROOT CAUSE
  internal/litellm/ HTTP client wraps the response body into the
  Go error but the reconcilers only call err.Error() with the
  generic "litellm: 400 on POST <path> (code=400)" formatting and
  drop the body.

FIX
  Capture the response body (first ~256 bytes, truncated) into the
  error type returned by the HTTP client (e.g. add a `.Detail()`
  method on the typed error) and include it in
  meta.SetStatusCondition's Message. Truncate aggressively — the
  condition message has a soft k8s limit around 32KiB but
  `kubectl get -o wide` truncates at ~80 chars, so keep it short.
  Already-known reasons should still go to the structured `Reason`
  enum (LiteLLMRejected, SecretNotFound, …) so the rich detail
  goes in Message only.

[HIGH-9] REGRESSION: v0.1.2 upgrade breaks every manual MCPServer
         whose K8s name has hyphens (no dots). Sanitizer renames the
         LiteLLM-side server_name to a dotted form that LiteLLM rejects.
────────────────────────────────────────────────────────────────
SYMPTOM
  test-exa-mcp (Ready=True since 2026-05-21 pre-v0.1.1) flipped to
  Ready=False reason=LiteLLMRejected immediately after the v0.1.2
  Helm upgrade (revision 2 at 13:31:25Z). Last reconcile at 13:32:00Z:
    op = PUT /v1/mcp/server
    error = "litellm: 400 on PUT /v1/mcp/server (code=400)"
  This is a strict regression — the CR was happy under v0.1.1 and the
  upgrade alone (no spec change, no CR edit) broke it.

EVIDENCE
  - LiteLLM-side server still exists under the ORIGINAL name. Direct
    probe (2026-05-22T13:45Z):
        GET /v1/mcp/server → "server_name":"test-exa-mcp" (present)
  - Operator-side: CR.status.lastRendered.ServerID =
    72452234-c5ec-4a9e-8e25-da41f02d422b (the pre-v0.1.1 record).
  - Operator now sends a SANITIZED name on every reconcile:
        SanitizeMCPServerName("test-exa-mcp", "-")  →  "test.exa.mcp"
    because Connection.spec.mcpToolPrefixSeparator defaulted to "-".
  - LiteLLM probe with dotted name → same 400 we observed for the
    discovery children:
        {"detail":{"error":"Server name cannot contain '.'."}}
  - LiteLLM probe with hyphenated name (different alias) → 201
    accepted (test-exa-mcp-probe2 created successfully then cleaned up).
  - Existing LiteLLM /v1/mcp/server entries that ARE Ready and have
    hyphens: google-calendar, google-calendar-oauth, google-drive,
    zoho-desk-ro, zoho-projects-ro, … (14 servers with hyphens).
    Conclusively: LiteLLM v1.85.1 ACCEPTS "-" in server_name and
    REJECTS "." regardless of MCP_TOOL_PREFIX_SEPARATOR env value.

ROOT CAUSE
  Combination of two design choices that are wrong-by-default:
  (a) `+kubebuilder:default:="-"` on Connection.spec.mcpToolPrefixSeparator.
  (b) Sanitizer always rewrites when separator is set, even when the
      input name does NOT contain the forbidden character. The "-"
      default flips every "-" to "." unconditionally — so a name
      already safe ("test-exa-mcp" has no dots) gets mangled.
  Either alone would be a soft footgun; together they produce a hard
  regression: upgrading the operator silently changes the LiteLLM-side
  server_name for every manual MCP in the cluster.

FIX
  Make the sanitizer a no-op on already-safe inputs:
    func SanitizeMCPServerName(name, separator string) string {
        forbidden := separator  // the char LiteLLM rejects
        if forbidden == "" { forbidden = MCPToolPrefixSeparatorDefault }
        if !strings.Contains(name, forbidden) {
            return name      // no rewrite needed
        }
        var replacement string
        switch forbidden {
        case ".": replacement = "-"
        case "-": replacement = "."
        default:  return name
        }
        return strings.ReplaceAll(name, forbidden, replacement)
    }
  This preserves behavior for inputs that ACTUALLY contain the
  forbidden char (discovery children with dots when separator=".")
  but stops mangling names that were already valid.
  Combined with HIGH-1 (default flip to "."): with the new default,
  the sanitizer only rewrites when an input contains "." — exactly the
  problematic case.

  Migration path for existing affected manual MCPServers:
  - Detect LiteLLM-side orphan by comparing
    status.lastRendered.ServerID with what GET /v1/mcp/server returns
    for the SANITIZED name. If the sanitized name has no entry but
    the original name does, the operator should adopt the original
    record (use the server_id from the original entry) — same idea
    as the existing resolveServerIDByName probe at
    mcpserver_controller.go:162, but extended to also try the
    PRE-SANITIZE name on lookup.

TEST PLAN
  1. Unit: SanitizeMCPServerName("test-exa-mcp", "-")
     • Old behavior: "test.exa.mcp"
     • New behavior: "test-exa-mcp" (unchanged because input has no ".")
  2. Unit: SanitizeMCPServerName("a.b.c", "-") → "a.b.c" (unchanged)
     (sep="-" means LiteLLM forbids "-"; input has no "-" so no rewrite)
  3. Unit: SanitizeMCPServerName("a.b.c", ".") → "a-b-c"
     (sep="." means LiteLLM forbids "."; rewrite to "-")
  4. Unit: SanitizeMCPServerName("a-b-c", "-") → "a.b.c"
     (sep="-" means LiteLLM forbids "-"; rewrite to ".")

[LOW-12] kubebuilder defaults (mcpToolPrefixSeparator) don't get
         applied to existing CRs through Flux/GitOps
────────────────────────────────────────────────────────────────
SYMPTOM

  its on-disk YAML or apiserver representation, despite
  `+kubebuilder:default:="-"` in the Go type. kubectl get -o yaml
  shows the spec WITHOUT the field. Operator code reads the snapshot
  and sees empty string, which the sanitizer treats as "-".

EVIDENCE
  - kubectl get litellmconnection default -n ackstorm -o yaml shows
    spec: {endpoint, masterKeySecretRef}. No separator field.
  - The CR's manifest is owned by Flux (label
    kustomize.toolkit.fluxcd.io/name=apps-alitellm-operator-post).
    Flux strips unset fields on diff/apply, so the kubebuilder
    default — which the apiserver populates ONLY at create/update
    time — gets continually drift-reconciled-back-to-absent.
  - Net effect: the kubebuilder default exists but is not the
    *effective* value the operator sees. The "default" branch in
    SanitizeMCPServerName (separator=="") fires instead.

ROOT CAUSE
  CRD defaults via OpenAPI schema (kubebuilder:default) only land
  on the object at server-side create/update if the field is missing
  in the incoming request. Flux + SOPS pipelines that strip empty
  fields can interact badly: the operator's effective behavior is
  driven by the literal stored value, which is empty after Flux.

FIX
  Make the operator's snapshot loader treat empty
  Connection.spec.mcpToolPrefixSeparator as the intended default
  ("-") loudly — log once per Connection that the default was applied
  AT RUNTIME with the resolved value. Then HIGH-1 (flip default to
  ".") becomes a single code change with no GitOps surprise.
  Optional belt-and-braces: a CEL validation that *requires* the
  field if mcpserver CRs exist in the namespace.

TEST PLAN
  1. Unit on the snapshot loader: empty input → loader output has
     MCPToolPrefixSeparator set to the new default.
  2. envtest: Connection without the field → sanitizer behaves as
     if default was set.
  3. Doc: explicit note in the user guide about always pinning the
     field in the manifest under GitOps tools.
